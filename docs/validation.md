# 目前的验证情况

在真实工位数模上的验证数字：与设计阶段逐项对照的主表、抽样波动的论证、交付默认口径下的覆盖率、工位自检报出的问题，以及合并后的三档实测。

在**真实工位数模**上跑过两轮，结论与设计阶段的四轮可行性验证一致：

| 检查项 | 设计阶段（8 mm 网格） | 本次实现复跑（8 mm） |
|---|---|---|
| 上面面积 | 1.0544 m² | **1.0544 m²** |
| 下面面积 | 1.0511 m² | **1.0511 m²** |
| 剪切断面 | 0.0117 m² | **0.0118 m²** |
| 镜像对面命中率 | 99.1% | **99.1%** |
| 定向种子 / 传播 | 88.9% / 99.4%（9 轮） | **88.9% / 99.4%（9 轮）** |
| 料厚（中位） | 0.698 mm | 0.678 mm（光线起点偏置 0.02 mm 所致） |
| 覆盖率 | 99.10% | 99.48%（同一张面、不同抽样，见下） |
| 视点数 | 50 | **50** |

> **覆盖率那一行的 0.38 个百分点不是算法差异，是抽样差异。** 两条依据：
> 一是本实现复刻了第四轮的候选阶梯（同一份配置、逐项相同），两者算出的
> 覆盖率完全一致；二是把**第四轮报告里自己的 154 个漏点**拿来，用本实现的
> 判定规则和一份**逐行照抄的第四轮规则**分别过一遍（同点位、同法线、同求交
> 器）：154 个点的结论**逐点一致，0 处分歧**。差异来自抽样：第四轮抽到的是
> 17033 个点，本次是 16937 个，两套点不是同一批（第四轮的漏点距本次最近的采样
> 点中位 3.32 mm）；而 8 mm 网格下"成型侧壁"那种 1–2 mm 宽的特征上谁被抽中、
> 谁被留下，本身就是抽签。设计阶段记的是同一件事：未播种时同一个输入，覆盖率
> 在 **99.10%–99.48%** 之间跳。本实现三次播种（7/11/13）得 99.48/99.52/99.55%，
> 波动集中在 `never_in_view`（31/17/16），其余成因稳定。
>
> 结论：**把覆盖率当"约 99.5% ±0.1"读，不要追第三位小数**，也没必要为了对上
> 第四轮那个数去改判定规则。

有两条结论影响了设计，也在复跑中重现：

- **固定的单台跟踪器本身不构成瓶颈**，前提是它沿**零件薄轴**方向架设，而不是正对大面
  看过去——机理是零件本体挡住了**扫描头**，不是跟踪器视场角不够；
- 残余漏扫是**二十来处小特征**（窄槽、小凹坑内壁），而不是一整片够不到的区域。

在**交付默认口径**（3 mm 采样网格 + 由粗到细补候选 + `--face auto`）上：

| | 上面（`auto` 选中的） | 下面（对照） |
|---|---|---|
| 贪心集合覆盖后 | 99.50%（103 点） | 91.29%（107 点） |
| 补一轮候选后 | **99.71%（111 点）** | 96.66%（140 点） |
| 补第二轮后 | 99.71%（117 点，只多盖 5 个采样点，第三轮不再获准） | 96.77%（146 点） |

两件事因此有了实测依据：

- **收益在候选密度，不在选择算法**：补一轮把上限抬了 0.21 个百分点（上面），下面抬了
  5.4 个百分点。集合覆盖本身早就把"池子够得着的地方"全盖住了，所以"补齐"那一阶段在
  实测里是空的——**视点数是被候选生成限制的**。
- **"哪一面朝上"的自动判定**用两面各算一次可达性来做：上面 99.71% vs 下面 96.77%，
  差距明显，与设计阶段的结论一致。

一个**取舍**留在这里，因为它是"覆盖率优先"这条排序规则的必然结果：第二轮补候选只多盖了
5 个采样点（119480 中的 0.004%，约 44 mm²），却多要 6 个视点。实现按"先比覆盖率、再比视点
数"取舍，所以留下了 117 点这一版。不想为千分之几个点付 6 个位姿的场合，可以把
`refine_rounds` 设成 1。

这些数字依赖占位的 `max_incidence_deg`，只能当**指示性**参考，因此这里刻意不写出具体数值。
抽样本身还会带来几个千分点的波动（见上一节的说明），所以**报覆盖率请带"约"字**。

## 工位自检在真实数模上报出来的问题

`plan` 每次都先跑一遍工位自检：三套数模是不是真的按工位文件说的那样坐在一起。在真实工位
数模上它报出的是：

> 零件有 **16 个网格点**钻进了夹具内部，最深约 **1.7 mm**（最深点坐标、探针点数与判定依据都写在
> `output/*/coverage_report.json` 的 `alignment_checks` 里，那一层是 gitignore 的）。

这与设计阶段的怀疑一致——**夹具数模是设计版，现场实际夹持区不同**——所以要现场确认夹具
到底压在哪里、是否真的与零件干涉。设计阶段当时自检的结论是"无干涉，最小面间距
0.204 mm"，但那个判据是面到面的距离，**看不见几毫米的穿透**；本实现改成有符号判据（零件
表面点落在夹具表面之后，且对附近每一片夹具表面都成立）。

这个判据现在是**确定性的**：它走两套数模自己的几何（零件的顶点与面心，再加按预算铺的面内
格点），一个随机数都不抽，所以换种子答案不变。两处仍然看不见的情况写在
[`scene.py`](../src/scanplan/scene.py) 的注释里：整块零件完全埋在夹具体内，以及夹具网格法线
整体反号。

## 合并后的三档实测（2026-10-23）

> **关节门那一行已作废，需重跑。** 2026-10-23 晚重新标定后发现，当时配置里的
> `tool_xyz_mm` / `tool_ypr_deg` 与示教器上的 `UTOOL 1` 相差 176°，也就是说下面"加
> `configs/robot_gate.json`"那一行的可达性判读是在一个法兰朝向翻了 180° 的模型上做的：
> 用新采的 8 组实测位姿反考旧模型，4 组无解、另 4 组的 J5 符号与实测相反。机理与证据见
> [robot-calibration.md](robot-calibration.md)。工具已按新数据重标，这一行必须重跑后替换，
> **不要引用**。

两份设计合并落地后，在同一份真实数模上（上表面、`face=auto`、3 mm 采样网格）跑了三档：

| 档位 | 覆盖率 | 点数 | 条带 | 关键指标 |
|---|---|---|---|---|
| 出厂 `scanner_trackscan49.json` | 99.07% | 33 | 7 / 386 候选 | 池上限 99.63%，约 12 min |
| 加 `configs/robot_gate.json` | 99.03% | 66 | — | 0 个点无解、每点离限位 ≥5.00°、J5 全在 40–120°、11 种 CONFIG、约 10 min |
| `configs/legacy_exhaust.json`（回归） | 99.75% | 438 | 32 / 489 候选 | 与合并前的记录同量级 |

四条读数：

- **打开关节门几乎不花覆盖率**：99.07% → 99.03%，池上限两边都是 99.63%。
- **但点数翻倍**（覆盖点 33 → 66，过渡点 13 → 33）：关节可行把可选位姿压窄了，覆盖同一张
  面要用更多交付点。这是"用点数换真实可达性"，不是回归。
- **66 个点全部有逆解**（`points_without_solution: 0`），关节离限位最近的还有 5.00°，J5 全部
  落在 40–120° 这一带里。代价是 **14 段**相邻关节步超过 `max_step_deg = 40`（最大 171°）——
  这条按设计**只报不拦**（阈值没有现场依据），导入 ROBOGUIDE 时重点看
  `kinematics.steps_over_limit` 指出的那几段。
- 这一次硬门**没有丢任何条目**（`dropped_by_hard_gate: 0`）：把"过渡点解得出逆解"折进抬刀
  高度搜索之后，长扫描带的抬刀点也在可达空间里找到了位置。调参过程中曾出现丢 10 个条目的
  中间状态，根因是抬刀方向沿 `-axis`（背离零件）——这条路径仍值得下一步改成朝零件中心退。

运动学本身是用实测位姿标定的（2026-10-23 那批 8 组：位置残差 ≤0.02 mm、姿态 ≤0.002°，
留一交叉同量级；流程见 [robot-calibration.md](robot-calibration.md)），逆解在 300 组随机
位姿上往返全通过；`legacy_exhaust` 仍是可用的回归金标（438 点 / 99.75%，与合并前记录的
405 点 / 99.74% 同一量级）。

## 路线风格与两项新不变量（2026-11-01，**待实测**）

这一节只记"要量什么、怎么读"，**没有数字**——这三条都还没在真实工位上跑过，不要引用这里的
任何结论当验收依据。

**两档路线（`stroke.route_style`）。** `direct` 是之前的行为，`tidy` 换成"直线直飞 + 8 向侧移"。
要量的是同一零件、同一 seed、同一 `--fast` 下的七个数：

| 数 | 从哪读 | 说明 |
|---|---|---|
| 点数 / 过渡点数 | `viewpoints`、`viewpoints_transition` | `tidy` 预期过渡点明显减少 |
| 连接器分布 | `program.connector_levels` | `L0-straight` 占比是"直飞生效"的直接证据 |
| J 指令数 | 数 `.LS` 里的 `J` 行 | 直飞把 3 条指令压成 1 条 |
| 换族次数 | 报告里的 CONFIG 序列数相邻不同位 | 族罚生效后应下降 |
| 覆盖率 | `coverage_pct` / `delivered_pct` | **两档不能互相作为回归基准** |
| 耗时 | `runtime.seconds` | 侧移最多试 8 方向 × 抬升档，只在直线被挡时付费 |
| 关节审计 | `joint_audit.ok` | 两档都必须是 `true`——不许"整齐但导不出去" |

**读数前先确认三个前提**：1) 两档用的是同一份现场坐标系；2) `coverage_target_pct` 相同
（否则比的是验收口径而不是算法）；3) 报告里 `route.style` 与你要引用的档位一致。

**位姿不得埋在零件里。** 看 `evaluation.rejected_inside_part` 与 `evaluation.inside_part_unchecked`：

- 两个都是 0 → 检查跑了，这个工位上没有这类位姿（正常）；
- `rejected_inside_part > 0` → 之前有位姿在拿测不出来的覆盖率，这一版把它们去掉了，
  覆盖率**变化是修正**，不是回归；
- `inside_part_unchecked > 0` → 这个网格的奇偶判据不可信（或用了 `--no-occlusion`），
  这项检查没生效。此时**不要**把覆盖率变化归因于它。

**剪枝不再削穿达标集合。** 日志里出现 `pruning skipped: the selection sits at …%` 说明守卫生效；
没出现且点数明显少于选择阶段的条数，说明选择确实超了目标 0.5 个百分点以上，剪枝照常执行。
两种情况都正常，要区分开的是"点数变多"到底是守卫还是别的原因。

**J6 的两个收费口和那道兜底（2026-11-01 新增，同样待实测）。** 前提只有一条：先确认报告里
`kinematics.j6.available` 是 `true`。它不是就说明 `robot.enabled` 还是 `false`，下面所有数都没有
意义——模块 10/12 整段没跑。

**规划模式 `banded`（2026-11-01 新增，快跑已验证、正式网格未验证）。** 换模式之后先看三行：

| 数 | 从哪读 | 怎么判断 |
|---|---|---|
| `stroke_plan.delivered_strokes` / `delivered_stops` | 报告 | **「几条带 + 几个停点」**。`banded` 的目标是把停点压到 0；实测同一工位 99% 目标下从 5 带 + 18 停变成 11 带 + 3 停（门开）/ 11 带 + 0 停（门关） |
| `program.interrupts.reorient` | 报告 | 应该跟着降。实测 22 → 13（门开）/ 9（门关） |
| `route.plan_mode_settings` | 报告 | 记录实际生效的五个数；**两个不同模式的覆盖率不能互相作为回归基准** |

`banded` 的两个已知代价，验收时必须一起看：

- `kinematics.min_margin_deg` 会掉到 0.03° 量级——这是模式的本意（不再自设舒适区），但它意味着
  **贴着控制器限位跑**，ROBOGUIDE 里必须复核。`standard` 档是 5.4°。
- `kinematics.j6.literal_max_deg` 可能变大：实测 `banded` 有一次 132.4° 的 J6 换向，而 `standard`
  最坏 48.6°。倾斜带的空间朝向更杂，排序给 J6 计价只有 `tidy` 档开着（10 mm/度）；若这个数不可接受，
  先把 `stroke.order_j6_weight_mm_per_deg` 抬到 20 再跑一次。

**倾斜种子族是否真的活了。** 2026-11-01 之前它是死的（光轴算反，朝零件背面）。一条快速自检：
`trace` 一次 `side_scan_seeds` 的光轴与内法向夹角，应当等于 `side_scan_tilt_deg`（45°），不是 135°。
活的族会在 `banded` 档把带铺到 `x` 全宽、倾角 3°–85°；死的时候所有带都是同一侧、倾角 12°–27°。

跑起来之后按这个顺序读：

| 数 | 从哪读 | 怎么判断 |
|---|---|---|
| `j6.literal_total_deg` | 报告 | J6 字面总行程。开 `j6_travel_weight` 后应下降；不降说明**没有可选项**（见下一条） |
| `j6.worst` / `literal_max_at` | 报告 | 最坏单段在哪。和 `over_cap` / `over_report` 对得上才算读对 |
| `j6.over_cap` | 报告 | 超 `j6_max_step_deg` 的段；出厂配置里这个阈值是 `60.0` |
| `j6.over_report` | 报告 | 超 `j6_report_deg`（90°）的段，只是点名 |
| **`j6.physical_total_deg` / `physical_max_deg`** | 报告 | **唯一可比的口径**：它按姿态算，不看指令类型。`literal_*` 只数 `J` 段，一旦大量连接器改成 `L`，它就掉到很小，那不是改进，是没被计数 |
| 程序里 `J` / `L` 的条数 | 数 `.LS` | 2026-11-01 之后直线连接器写成 `L`，所以 `L` 的占比就是"路线有多直" |
| `path_length_mm` | 报告 | 排序给 J6 计价会拿它换：实测 J6 减半，绕行 +23% |
| 兜底日志 | 运行日志 | `point N: roll re-tried to hold the J6 step under 60 deg` = 真的换了滚转 |
| `branch_histogram` | 报告 | 只有一个键、且计数等于点数 → **每个位姿只有一个解**，权重与加法收费都不会有任何效果 |

最后一行是最容易误读的：`wrist_flip_policy = "T"` 下 64/64 个位姿只有一个解，DP 无从选择，
于是 `j6_weight` 和 `j6_travel_weight` 都不会改变结果，**这不是键没生效，是唯一解**。要验证收费
逻辑本身，得把策略临时改成 `any` 跑一次对照（那条路会引入 F 分支，不能交付，只用来量数）。

# 按模块看三个分支：差在哪，最后用了谁

这份文件回答一个问题：**从工件到 .LS 程序的这条链，拆成模块之后，三个分支各自做了什么，
合并时采用的是谁的。**

不写提交号、不写行号；那些在 [`merge-notes.md`](merge-notes.md) 里。这里只讲"这个模块负责什么、
三支的差别是什么、为什么最后落在这个取值上"。

三个来源并列，下文简称：

- **A** = `feature/modelbase3-update`
- **B** = `feature/joint-audit-and-config`
- **C** = `feature/joint-direct-connector`

---

## 管线全景（模块 1 → 12）

```
工件(CAD/STL) + 工位(夹具/底座/追踪器) + 机器人参数
   │
   1 参数与开关 ────────────── 决定后面所有模块"允许做什么"
   │
   2 工位载入与几何清洗 ─────── 对齐自检、面片绕向、双面分割
   │
   3 目标面采样 ────────────── 哪些点要测、哪些点夹持区可以豁免
   │
   4 候选位姿生成 ──────────── 围绕每个瞄准点摆出"可能的扫描头位姿"
   │
   5 可达性判定 ────────────── 逆解、限位、腕部奇异、逐段行走
   │
   6 覆盖评估 ─────────────── 这个位姿到底能扫到哪些采样点
   │
   7 视点选择 ─────────────── 用最少的视点覆盖目标（贪心集合覆盖）
   │
   8 扫描带生成 ────────────── 把相邻视点连成"一路扫过去"的直线段
   │
   9 路径排序与连接 ────────── 排序 + 两条带之间怎么过去（不撞件、不超限）
   │
  10 关节分配与读数 ────────── 每个点用哪组关节角、程序里写哪个数字
   │
  11 交付与校验 ────────────── 写成 .LS、写之前查一遍能不能飞
   │
  12 报告与产物 ────────────── 覆盖率、失败归因、3D 视图
```

**9 和 10 是"路径生成"真正的核心**，也是三支差别最大的地方。

## 逐模块对照

### 1 参数与开关

干什么：决定"门开不开、量程用多少、J6 怎么计价、程序怎么飞"。它不写算法，但决定了所有算法的输入。

| | A | B | C |
|---|---|---|---|
| 关节门默认 | **开** | **开** | **关**（保留可复现的旧结果） |
| 可用量程 | 量程 ×1.0 + 余量 5° | 量程 ×1.0 + 余量 5° | 量程 ×0.9 + 余量 5° |
| 腕部分支 | 字母钉死 T（但解集不过滤） | 字母钉死 T 且当约束过滤 | 只准 T（J5 负） |
| J6 | 常量 0.5，不可配 | 权重 1.5 + 上限 60° | 权重 1.0（等于不管）+ 报告 90° |
| 覆盖率目标 | 95% | 99% | 90% |

**采用**：C 的三项参数取值（0.9 量程 + 5° 余量 + 只准 T）+ B 的 J6 权重 1.5 和上限键。
新增三个开关：`scanner.roll_mode`（滚转策略）、`stroke.connector`（连接器策略）、
`stroke.route_style`（前两者的**成组预设**，见下方 2026-11-01 追加）。

为什么：0.9 量程是 C 实测"离限位 3° 就 hold 不住"之后收的，A/B 都是 1.0，属于未收；
J6 权重只影响"有多个解时选哪个"，取 B 的 1.5 没有副作用。

### 2 工位载入与几何清洗

干什么：把三套数模放到同一坐标系并自检；判断哪些三角面属于薄板的哪一面。

| | A | B | C |
|---|---|---|---|
| 对齐自检 | 有 | 有 | 有 |
| 面片绕向修复 | 无 | **有**（`winding.py`） | 无 |
| 网页点选补充面 | **有**（`ScanRegion`） | 无 | 无 |
| 退化射线/超大网格保护 | **有** | 无 | 无 |

**采用**：三支共有的对齐自检 + B 的绕向修复。A 的两项**这次没并入**。

为什么绕向修复必须进：不修的话，"upper 面"里可能混进 39% 的背面，夹具豁免会把半张面吃掉，
覆盖率数字从第一步就不可信。A 的两项要改覆盖率分母和 3D 视图的数据格式，属于"阶段 1 整版"，留到下一版。

---

### 3 目标面采样

干什么：在目标面上铺采样点；夹持区附近的点可以被豁免（现场不量那里）。

三支做法**几乎一样**。唯一差别：B 额外把"硬特征"（窄槽、贴夹具的边缘）单列一个覆盖率分母，
并在后面补扫；A 额外支持"网页点选一块面加进来"。

**采用**：三支共有的采样 + 夹具豁免；硬特征与点选面未并入（同上，改分母）。

---

### 4 候选位姿生成

干什么：对每个瞄准点，按"距离 × 倾角 × 滚转"摆出一堆候选位姿，然后截断到预算。

| | A | B | C |
|---|---|---|---|
| 关节门在哪一步 | 截断**之前** | 截断**之前** | 覆盖评估时（**晚**） |
| 滚转 | 0°/90° 全摆 | **按光轴锁定一个**，门拒绝时按固定顺序回退 | 0°/90° 全摆 |
| 截断方式 | 每个瞄准点轮流取 | 每个瞄准点轮流取 | 按 seed 随机抽 |

**采用**：A/B 的"门前置" + 轮流截断 + B 的"锁定滚转 + 回退"，并做成可切换的插槽（`roll_mode`）。

为什么门前置：截断预算是几千个位姿，门放在评估期意味着**先花完预算再筛**——一次交付里 786/4000 个候选是白算的。
为什么锁定滚转：0°/90° 混摆会在两条带之间制造 74–95° 的 J6 转动，对扫描没有任何好处；
但锁定会让少数位姿不可行，所以保留固定顺序的回退（45/315/90/…），而不是一刀切。

---

### 5 可达性判定

干什么：给定一个位姿，判断机器人能不能摆出来、离限位还有多少、沿直线走会不会中途丢分支。

这是三支**共同祖先**就有的部分（逆解 + `KinematicGate`），差别在**严格程度**和**逐段验证**：

| | A | B | C |
|---|---|---|---|
| 逆解 | 解析解 | 解析解 | 解析解 |
| 单点判据 | 限位 + 1.0 + 5° | 限位 + 1.0 + 5° | 限位 + 0.9 量程 + 5° |
| 逐段行走验证 | **无**（只查角点） | 有（`move`，L 采样 + 分支跟随） | **有**（`follow`，10 mm 采样、锁分支） |
| 腕部过零（J5=0） | 完全不检查 | 排序里罚 1000° | **硬拒** |

**采用**：C 的"0.9 量程 + follow 逐段验证 + J5 过零硬拒"。

为什么：`X10290` 那次报警是"两个端点都合法、中间丢分支"，只有逐段行走才发现得了；
J5 过零是腕奇异，A 完全不检查，实测它会为了压 J6 把 J5 从 −106° 甩到 +108°（4 次过零）。

---

### 6 覆盖评估

干什么：对每个候选位姿，算它能扫到哪些采样点（视场、距离、入射角、遮挡、追踪器可见性）。

三支**一样**——都是"射线求交 + 追踪器可见性 + 夹具/底座遮挡"。差别只在"门在哪"（已在模块 4 说过）。

**采用**：三支共有实现 + C 原有的评估期兜底。

**2026-11-01 追加：A 的"参考点不能埋在零件里"检查已并入。** 三支都没有这一项之前，一个参考点落在
板材内部的位姿照样会拿到覆盖率——`measure_mask` 会隔着它自己所在的那层材料看见背面的采样点，
覆盖到的是根本测不出来的东西。现在评估前先用一次奇偶射线测试（三轴投票、至少两票）把它拒掉并计
`rejected_inside_part`。[A 的实现](merge-notes.md) 假设零件是闭合壳体，而真实零件实测
`is_watertight = False`（110k 面、euler −3517，细分面与整条边圈的 T 型接头是正常的），所以判据改成
**"这个网格能不能信奇偶"**：八个远在零件外的包围盒角点必须全判"外"，否则 `inside_part` 直接拒绝作答、
`evaluate` 不去调用，并计 `inside_part_unchecked`。

实测精度（2026-10-30 零件）：沿法向压进材料 0.15 mm 的探针只有 30% 被判内部（**召回不全**），
从面沿法向拉出 100–300 mm 的 600 个位姿**一个都没被误判**。否决权只要求后者。

---

### 7 视点选择

干什么：从合法候选里挑出最少的视点，把目标面覆盖到目标百分比；覆盖不够时再补一轮候选。

三支**一样**（贪心集合覆盖 + 覆盖率目标 + 补候选轮）。A 多一个"候选池为空时返回空选择而不是崩"的小修复；
B 多一个"硬特征优先"的权重。

**采用**：三支共有的贪心 + C 的补候选轮。A 的空池修复没并入（因为候选门前置后这个分支基本不会走到）。

**2026-11-01 追加：选择之后那一刀剪枝加了守卫。** 选择一越过目标就停手，超出量不到一条；从那里再剪
只会往下掉。A 记录了现场实测：对一个**已经达标**的集合执行剪枝，覆盖率从 99.04% 掉到 92.06%，
而报告里一条 `dropped` 都没有——因为没有任何条目是被硬门拒掉的，报告根本没有字段描述这件事。
现在先算一次被选中集合的并集覆盖率，落在 `目标 + 0.5` 个百分点以内就直接跳过剪枝并打印
`pruning skipped: …`，真正超目标时照旧剪。

### 8 扫描带生成

干什么：把相邻视点连成一段"一路扫过去"的直线（现场是连续扫，不是停稳再拍）。

三支**一样**。A 的 `strokes.py` 在 diff 里看起来改了 1600 行，但用 `-w`（忽略空白）看是 0 行——**只是换行重写**，
不是算法差异。这是最容易误读的一处。

**采用**：三支共有实现（C 的版本），滚转按光轴锁定。

---

### 9 路径排序与连接（差别最大之一）

干什么：决定先扫哪条带、每条的入口方向，以及**两条带之间怎么过去**——不撞零件、不超限。

| | A | B | C |
|---|---|---|---|
| 带间主手段 | 直连 + 侧向让位 + 安全面 | 直连 + 抬升阶梯 | **一次关节直连**（`J` 过去，不插点） |
| 直连失败后 | 侧向让位/安全面 | **抬升阶梯**（小抬升起步 0.35×，朝机器人拉回） | 退刀 L0/L1/L2、**安全面 L3** |
| 角点是否验证 | 只查角点 | 逐段验证 | 逐段验证 |

**采用**：C 的"一次关节直连"为第一级 + B 的"抬升阶梯"为第二级。安全面（L3）**删掉**。
A 的侧向让位和 B 的"朝机器人拉回"当时没并入（侧移后来作为可选的一档进来了，见本节末尾）。

为什么删安全面：它的角点是**插进去的点**，而"7 个不可达点全是自插角点"正是重写连接器的原因；
多一级兜底就多一批没人飞过的点。
为什么直连是主手段：关节插值每个轴都是线性的，两端合法就**不可能在中段出界**，所以既不需要退刀点也不需要 CONFIG。

**2026-11-01 追加：A 的"直线优先 + 垂直光轴侧移"作为第二个连接器进门了，但是可选的一档，不是默认。**
它就是 `stroke.route_style = "tidy"` 展开出来的 `straight-then-lateral`：直线通了就不插任何点（程序里一条指令
到位），被挡时在垂直于光轴的 8 个方向里找侧移等待点（侧移方向来自 A，理由也是 A 的：沿轴退刀走进上表面
背后的底座、下表面背后的工装），仍然不行才回落"关节直连 → 抬升阶梯"。

三处**没有**照 A 搬：

| A 的做法 | 我们的做法 | 为什么 |
|---|---|---|
| 直线被挡且侧移失败时**仍然飞直线**，只记一条 violation | 回落关节直连，绝不丢件也绝不穿件 | `hard_gate: true` 是"不合法就丢件"，两套"可交付"的定义不能共存 |
| 退刀 3 个方向（身后 / 法向外 / 朝机器人内拉） | 只做垂直光轴的 8 向；沿轴退刀留给 `direct` 档 | 内拉是缩短臂展的好主意，但只在**退刀**这条路线上有意义；`tidy` 档的兜底是关节直连，不经过退刀 |
| 安全面优先（跨朝向 >60° 时） | 仍未并入 | 它要 `build_path` 透传法向/平面、每个转角逐点逆解，收益与 `tidy` 档高度重叠，留给下一步按实测决定 |

为什么做成两档而不是替换默认：两档交换的是**点数**和**程序形状**，实测口径还没做。`direct` 对出厂配置是
恒等映射，所以不选风格 = 与之前逐字节相同。

**2026-11-01 追加二：两处让"整齐"真的落到程序上的改动。**

第一处是缺陷，不是新功能：连接器验完一条直线（间隙 + 跟踪器）返回 `LEVEL_STRAIGHT`，而交付阶段把到达点
一律写成 `J`，因为"门开着就该是关节移动"。验过的直线就这么被丢掉了——`J` 在关节空间插值，TCP 走弧线，
腕部按 IK 给的读数直线插过去。实测同一工位 30 个交付点：23 个连接器验的是直线，程序里却只有 4–5 条 `L`。
现在到达点的指令由连接器的结论决定（`path._arrival`），并且 `_cartesian_leg` 补上了两条验证，缺一条
`LEVEL_STRAIGHT` 就不成立：转弯速率（`L` 是边走边转）和 `KinematicGate.follow`（直线中途丢分支）。
结果：**3 `J` / 27 `L`**。

第二处是排序开始给腕转计价：`stroke.order_j6_weight_mm_per_deg`，在"行程 + 姿态变化"之外再加
"每度 J6 折多少毫米"。它之所以是**唯一有效**的 J6 旋钮，见模块 10 的追加二：模块 10 在同一位姿只有
一个解时无从下手，排序却始终有得选。同一批位姿只改顺序，J6 物理总和 1056° → 506°，最坏单段
175° → 62°，代价是绕行 10751 → 13240 mm。

**2026-11-01 追加三：一个新模式 `banded`，以及它查出的一处真缺陷。**

"为什么曲线板一侧全是扫描带、另一侧全是孤立停点"的答案不是取舍，是**一个死掉的候选族**。
`StrokesBuilder.side_scan_seeds` 的光轴写成 `-tilt_axis(-normal, tangent, tilt)`，那个负号让光轴
变成距内法向 **135°**（出厂倾角 45° 时），也就是朝零件背面看，入射余弦 −0.707。这一族长出的每条带
都覆盖不到采样，`_reaches_any` 第一步就判死——**模块 8 里"给侧壁用的倾斜族"从上线起就一条带都没产出过**。
改成 `tilt_axis(inward, tangent, tilt)`（与 `ladder` 的正对梯子同一写法）后它才活。

修完之后把它做成一个可选模式，叫 `stroke.plan_mode`，和 `route_style` 是两条独立的轴：

| | `standard` | `banded` |
|---|---|---|
| 倾斜族方向 / 间距 / 只铺墙 / 上限 | 1（2 轴）/ 200 mm / 全铺 / 不限 | 3（6 轴）/ 60 mm / ≥45° / 96 颗 |
| `robot.joint_span_fraction` / `joint_margin_deg` | 0.9 / 5.0 | 1.0 / 0.0 |
| `stroke.stroke_corner_cost` | 2.0 | 1.0 |

三件必须一起动，单独动任一件都量不出效果：① 有没有东西可选（候选族），② 选到的活不活得下来
（包络——`gate_ok` 是整条带判死，缩包络下生长候选从 216 掉到 43），③ 活下来的赢不赢得了单点（带价）。

实测（同一工位、10 mm 网格、99% 目标、都开关节门、都带 `tidy`）：

| | `standard` | `banded` |
|---|---|---|
| 生长候选带 | 37 | 281 |
| 交付 **带 / 停点** | 5 / 18 | **11 / 3** |
| 点数 | 31 | **27** |
| 换向中断 | 21 | **13** |
| 覆盖率 | 99.03% | 99.04% |
| 最小关节余量 | 5.37° | **0.03°**（贴限位，模式的本意） |
| 最坏 J6 换向 | 48.6° | 132.4°（需复核） |

那个 132.4° 是本轮唯一没解决的遗留：倾斜带的空间朝向更杂，而排序的 J6 计价只在 `tidy` 档开着。

### 10 关节分配与读数（差别最大之二）

干什么：每个交付点用哪组关节角；程序里那个数字写成多少（同一个姿态可以写成 +19.9° 或 −340.1°）。

| | A | B | C |
|---|---|---|---|
| 选解 | 分支 DP（另加常量 0.5×J6） | 分支 DP（J6 权重 1.5 + 超限罚 10000） | 分支 DP（价格 = 加权最大轴步） |
| 读数修正 | 单向贪心（从前往后一遍） | 单向贪心 | **整链瓶颈 DP**（全链一起选，先压最大步再压总行程） |
| 圈位（CONFIG 第 4-6 位） | 行程外才计圈 | 行程外才计圈、负值拒写 | `floor((j+180)/360)` |
| 字母与 J5 符号 | 钉死 T，**不过滤分支 → 10/10 不一致** | 钉死 T + 当约束过滤（一致） | 按物理符号派发（一致） |
| 超限 J6 的处理 | 只报 | 只报 + 排序罚分 | 只报（阈值 90°） |

**采用**：C 的**整链瓶颈 DP** + B 的上限（`j6_max_step_deg`）与圈位规则 + 新增一道兜底。
注意 J6 权重这一项实际采用了 **C 的乘法形式**，不是 A/B 的加法形式——两者压的不是同一件事，
见本章末尾的追加说明。

兜底（这次新写的）：整链 DP 之后如果还有超限 J6 步，**对非覆盖点重试滚转**（滚转不改变视场），
还压不下去就记录并交给速度梯次（>60° 一律 10%）。覆盖点不动它的滚转——那会改掉已验收的覆盖率。

为什么必须是整链 DP：A 的分支在同一台工位上跑过一次，交付里有**一段 J6 从 −349.9° 写成 −78.6°**，
等于让手腕空转 271°，而它的报告只写 103.9°（按环形差统计）。单向贪心一旦某点写成绕一圈，后面全被拖着走。
这也是这次合并**核心验收项**的由来：报告里的关节步长必须等于文件里的字面步长。

**2026-11-01 追加：换臂型开始计价了。** A 和 B 的 DP 里都有 `_CONFIG_CHANGE_COST_DEG = 240`，合并时
没搬，于是代价函数里"换臂型"这一项是 **0**——等于假设控制器甩整条臂是免费的。B 记录了实测：
2026-10-28 那份程序在扫描中间换过族，J1 甩出 167.6°、J3 甩回 158.8°。现在这变成两个配置键：

| 键 | 默认 | 语义 |
|---|---|---|
| `robot.config_change_cost_deg` | `0.0`（= 与之前一致） | 换族一次加多少度当量；**同一条带内部再加一倍**，因为带的两端是同一个姿态，那里换族不是偏好而是一次跳跃 |
| `robot.wrist_flip_cost_deg` | `180.0`（= 之前写死的常量） | J5 过零的代价 |

默认取 0 是刻意的：这是**计价**，不是**事实**。它不改变任何"能不能交付"的判断，只改变"等价时选哪个"。
`route_style = "tidy"` 会把两者展开成 `240 / 1000`。

**2026-11-01 追加二：J6 的两种收费形式，以及为什么"越小越好"这件事合并时退了一步。**

三家都想让 J6 少转，但写进代价函数的形式不一样，压的东西也就不一样：

| | A | B | C |
|---|---|---|---|
| 形式 | `max(Δi) + 0.5·ΔJ6` **加法** | `max(Δi) + w·ΔJ6` **加法** | `max(Δi , w·ΔJ6)` **乘法** |
| 权重来源 | 硬编码常量 | `stroke.j6_step_weight`（默认 0.5 / 出厂 1.5） | `robot.j6_weight`（默认 1.0） |
| 上限 | 无 | `stroke.max_j6_step_deg`，出厂 **60°**，超了罚 `10_000` | `robot.j6_max_step_deg`，默认 `null` |
| 兜底 | 无 | 无 | `ease_over_cap_j6()` 事后重试滚转 |
| 报告 | `max_j6_step_deg` 一个数 | `j6_over` 清单 + `max_j6_step_at` + 交付阶段日志 | `_j6_block`：杠杆臂、直方图、dominant_segments、literal/physical 双口径 |

差别在算术上是这样：手臂挪 100°、J6 转 20° 时，加法式收 `100 + 0.5×20 = 110`，乘法式收
`max(100, 1.5×20) = 100`——**乘法式对“没超过最大轴的那部分 J6”完全免费**。所以加法式压的是
**总 J6 行程**，乘法式只压**单次大跳**。真要"J6 越小越好"，需要的是加法式。

合并取了 C 的乘法式，于是 2026-11-01 之前的工作树里：`j6_weight` 出厂 1.0、乘法，A/B 的加法收费
没搬；`j6_max_step_deg` 出厂 `null`，B 的 60° 上限和 C 的兜底**双双休眠**；`j6_report_deg` 是**死键**
——配置注释和 `docs/configuration.md` 都说它驱动 `kinematics.j6.over_report`，而 `src/` 里没有任何
代码读它，报告块里也没有这个键（合并后用的是 B 的 `over_cap`，而 cap 是 `null`，永远空列表）。

补的三件事：

| 补了什么 | 为什么 |
|---|---|
| `robot.j6_travel_weight`（默认 `0.0`）= A/B 那一笔**加法**收费，作为**独立第二把旋钮** | 不改 `j6_weight` 的语义，所以默认行为逐项不变；想压总量就把两个都打开 |
| 报告块新增 `over_report` + `report_deg`，由 `j6_report_deg` 驱动，只列 `J` 段 | 纯报告，零行为变化。顺带修了 `literal_max_at` 原来在全段上取 argmax、而 `literal_max_deg` 只在 `J` 段上算的不一致 |
| 出厂配置写 `j6_max_step_deg: 60.0`；兜底加三道闸（不翻 J5、J6 以外不得更远、进出两段都过 `_joint_move`） | 上限开着才有兜底可跑；原来的兜底只挑"J6 更小"的解，可能用 120° 的 J1 换 130° 的腕转，而且只验进入、不验离开 |

还有一个必须记住的前提：这些全是模块 10/12 的事，**只有 `robot.enabled: true` 才跑**，而出厂配置
是 `false`（等 `_comment_robot` 里的 G1/G3）。所以出厂配置上它们是**记录下来的意图**。今天真正让
J6 不动的是模块 4/8 的滚转约定（`rolls.roll_for_axis` / `LockedRolls`）——它在种子阶段起作用，与门
开不开无关。这一条三家都有：B 在 `candidates.py` 和 `strokes.py` 里逐族守 `lock_roll`，C 把它做成
了策略槽位 `LockedRolls`，合并取的是后者。

## 三个"看起来像差异、其实不是"的坑

1. **`strokes.py` 改了 1600 行** —— A 那边只是换行重写，忽略空白后是 0 行。整支 A 的 diff 原始是
   +18143/−15101，`--ignore-cr-at-eol` 之后只剩 **+3566/−524**：**八成是行尾重写**，不是算法。
2. **逆解和关节门不是三支的差异** —— 三支共用一个祖先，差别只在"门的松紧"和"有没有逐段验证"。
3. **覆盖率目标 90/95/99 不是算法** —— 是配置里的验收口径，换个数字点数和覆盖率都会变，
   所以对比之前必须先对齐（这次实验统一设成"选到不再增长"）。

## 为什么是这套取舍

- **三支的现场证据量不同**：实测限位、8 组实测位姿标定、T/F 两次导入试验、连接器实机验证只发生在 C 上，
  A/B 停在离线对比。默认值因此取有现场闭环的那份，其余做成可选开关——这是按证据取舍，不是给三支排名。
- **B 的改动多为局部函数**：绕向修复、滚转回退、J6 价格、圈位规则、导出审计，接进去不动主干。
- **A 的改动多触及数据模型**：补充面和硬特征都要动"覆盖率分母 + 报告 schema + 3D payload"，
  按"先收敛、后扩展"的顺序，放在下一版更安全。
- **A 的合并成本还高在形式上**：单提交、从同一基线直接分叉、从未合并过 C，所以"挑几块接进来"实际是
  在重构过的代码上手工重放；这也是为什么它的两块修复（位姿不得埋在零件里、剪枝守卫）晚了两周才落地。

## 一、五个阶段与数据契约

管线仍然是单向的，但边界现在有名字了，写在 `src/scanplan/contracts.py`：

| 契约 | 谁产出 | 谁消费 | 为什么值得一个类型 |
|---|---|---|---|
| `RobotEnvelope` | 阶段 2 之前，`KinematicGate.envelope` | 阶段 2 的候选筛选、阶段 4 的分支选择、阶段 5 的审计与报告 | 机器人可用域只能有**一个**来源。以前它同时存在于候选筛选和排序代价里，两处各算一次就会漂移 |
| `GateVerdict` | `kinematics.check()` | 全部下游 | 布尔值 + 原因，报告才能按原因分组，而不是重跑一遍 IK |
| `ConnectorResult` | 阶段 3 的连接器 | 阶段 4 | 只给"转角点"不给"验证过的关节"的路由等于没验证；`verified` 属性把这点写死 |
| `DeliveredPoint` | 阶段 3/4 | 阶段 5 | `PathPoint` 与 `Viewpoint` 结构相同，`is_delivered_point` 是运行期检查，不强制转换 |

阶段 4 的插槽不是"再来一个策略"，而是参数：`RobotEnvelope` 是冻结的，任何阶段都改不了它。
这是 E1 那条评审意见的落地方式——**可达域不属于任何插槽**。

## 二、插槽（`src/scanplan/policies.py`）

| 插槽 | 实现 | 配置键 | 默认 |
|---|---|---|---|
| 滚转 | `LockedRolls`（光轴决定滚转 + 门拒绝时按 `ROLL_RETRY_DEG` 回退）/ `DiscreteRolls` | `scanner.roll_mode` | `locked` |
| 连接 | `ConnectorChain`（一级关节直连 → 二级抬升阶梯）/ `StraightThenLateral`（直线直飞 → 8 向侧移 → 回落前者的链路，2026-11-01 追加） | `stroke.connector` | `direct-then-lift` |

两个实现由 `stroke.route_style` 成组选择：`direct`（默认）展开成前者，`tidy` 展开成后者
并把换臂型/腕翻转计价一起调上去。`route_preset` 是唯一的展开点，网页与命令行都走它。

- 滚转插槽的默认是 `locked`：实测离散滚转会在带间制造 74–95° 的 J6 转动，对扫描没有收益；
  但锁定会让少数位姿不可行，所以保留固定顺序的回退（45/315/90/…），而不是一刀切。
- 连接插槽只剩两级。旧的 `L3` 安全面路线**已删除**：它的角点是插进去的点，而"7 个不可达点全是
  自插角点"正是重写连接器的原因。抬升阶梯的起步档从 1.0× 降到 0.35×/0.6×（小抬升更容易可达）。
- 两个插槽都只有**一个**生产实现。第二个实现等第二个站点需要时再加；提前建插件层等于给没人跑过的
  代码发长期维护许可证。

## 三、逐项的合并决定

### 阶段 1：几何
- 并入 B 的 `winding.py`（面片绕向修复），在 `scene.load_models` 里、任何下游读 `face_normals`
  之前执行；结果写进 `Station.winding` 和报告的 `part_winding` 块。
- **未并入**：B 的硬特征梯次覆盖、A 的交互补充面（`ScanRegion`）。原因见第五节。

### 阶段 2：候选
- 关节门从"评估期过滤"改成"`_cap` 之前过滤"（`candidates.generate(keep=...)`）。
  旧行为会把预算花在端不住的位姿上：一次交付里 786/4000 个候选是白算的。
- 候选截断从"按 seed 随机抽"改成"每个瞄准点轮流取一个"（`candidates.cap`）：
  随机抽样会让整片区域一个候选都没有，而**没有候选的区域永远不可能被覆盖**。

### 阶段 3：连接器
- 责任链压缩为两级（见上）。`_safe_plane` / `_cross_group` / `_crosses_direction` 一并删除。
- 门关时的行为保持不变（`connector_level == 0` 仍然允许同姿态直飞），
  因为"关门等于回到旧行为"是这个项目的回归口径。

### 阶段 4：分支与读数
- **圈位规则换成 B 的**：`turn_digits` 只在轴自身行程之外才计圈，负圈位返回负值由导出端拒写。
  旧规则 `floor((j+180)/360)` 会给 −284° 的 J6 写 `-1`，而 FANUC 没有负圈位，ROBOGUIDE 整份拒收（ASBN-009）。
- **J6 上限成为价格**：`robot.j6_max_step_deg`（默认 `null`，出厂配置未开启）超过即加
  `_J6_OVER_CAP_COST = 10000` 的罚分。仍然不拦——拦等于丢掉那条带的覆盖率。
- **J6 权重默认值从 1.0 提到 1.5**（B 的值）。它只在"有第二个解"时起作用，不会让不可行的变可行。
- **E3 的兜底**：`ease_over_cap_j6` 在整链 DP 之后跑，只对**非覆盖点**重试滚转（覆盖点的滚转决定
  它扫到哪些采样点，改它等于改已验收的覆盖率）；仍压不下去就记录违规，由速度梯次把它压到 10%。
- 分支过滤本来就是物理的（按 J5 符号过滤，不靠渲染字符串），这一点没有回归：
  实测导出的 4 个点 CONFIG 与 J5 符号 0 处不一致。

### 阶段 5：交付
- **导出前审计**（`adapt.export`）：
  - `validate.check_points`：独立 Robot、无规划器缓存，逐条指令重走一遍；
  - `validate.check_config_hints`：CONFIG 列与它声称的关节是否一致（负圈位、腕字母）；
  - 新增 `joint_pose_mismatch`：关节块与同一点的 XYZ 对不上，说明写的和算的不是同一个点。
- 有任何一个失败 → **不落盘任何 `.LS`**；`--allow-unverified` 才能生成"仅供审阅"的文件，
  并且 `_frame.json` 里记 `joint_audit.allowed_by_override = true`。
- 只有**声称带有joint evidence** 的文件才因可达性被拒：纯位姿交付的可达性按文档约定由 ROBOGUIDE 判定，
  在那里拦会把一条已文档化的流程悄悄废掉。CONFIG 列则永远检查，因为它总是会被写出去。
- 报告升到 `schema_version = 2`：关节步长按**指令类型**统计——`J` 用程序里写的字面值，
  `L` 另列 `cartesian_segments`（直线运动的端点关节差不代表任何真实动作）。
  `max_step_circular_deg` 保留为诊断字段。

### 第二轮：J6 的四道闸与扫掠优先模式（2026-11-01 晚）

这一轮的起因是现场的两句话："J6 还是爱转，三个点的时候反复转"、"一侧是扫描带，另一侧全是停点，
B 的算法能铺满"。第一句落在模块 10/12，第二句落在模块 8，但两者最后都是**同一个病**：
旋钮和分支都在，代码却没接到（或者接错了方向）。

#### 一、J6 轴旋转限制：四个旋钮里三个是死的

| 旋钮 | 当时的状态 | 后果 |
|---|---|---|
| `robot.j6_report_deg` | **没有任何代码读它**（配置注释和 `docs/configuration.md` 都说它驱动 `kinematics.j6.over_report`，而报告里根本没这个键） | 想"只列清单、不加价格"地看 J6 大动作，没有入口；实际生效的是 B 的 `over_cap`，而它的阈值 `j6_max_step_deg` 是 `null`，永远是空列表 |
| `robot.j6_max_step_deg` | 出厂 `null` | B 的 60° 上限（单价 10000 的罚分）和 C 的 `ease_over_cap_j6` 兜底**双双休眠** |
| `robot.j6_weight` | 乘法式 `max(Δi, w·ΔJ6)` | 只对"J6 是本次动作最坏的轴"收费，一串 20° 的小扭完全免费。A/B 用的是加法式 `max(Δi) + w·ΔJ6`，那才是压**总行程**的形式 |
| `order_j6_weight_mm_per_deg` | 出厂 0.0 | 排序完全不看 J6——而这台机器上它是**唯一**能动 J6 的杠杆（下面说为什么） |

"唯一杠杆"这条是实测出来的，不是推断：`wrist_flip_policy: "T"` 下每个交付位姿只有**一个**关节解
（64/64 实测），所以模块 10 的分支搜索没有可选项，`j6_weight`、上限、兜底在本工位上是惰性的；
扳动姿态的只有排序阶段的重量。同一份 30 点多解实验：

| 排序的 J6 计价 | J6 总行程 | 最坏单次 | 代价（行程） |
|---|---|---|---|
| 只算行程（`order_j6_weight = 0`） | 1353° | 175° | 基准 |
| 默认（原样） | 1056° | — | — |
| `+10 mm/deg` | **544°** | 63° | +8% |
| `+20 mm/deg` | **409°** | — | +16% |

补的四件事：

1. **`robot.j6_travel_weight`（默认 `0.0`）**——A/B 那一笔加法收费，作为**独立第二把旋钮**接进
   `_step_cost`。不改 `j6_weight` 的语义，所以默认行为逐项不变；想压总量就把两个都打开。
2. **`j6_report_deg` 接通**——`kinematics.j6.over_report` / `report_deg`，只列 `J` 段。顺带修了
   `literal_max_at` 原来在**全段**上取 argmax、而 `literal_max_deg` 只在 `J` 段上算的口径不一致。
3. **出厂配置写 `j6_max_step_deg: 60.0`**——上限开着，B 的罚分才真的是一条价格。
4. **兜底加三道闸**（`ease_over_cap_j6(..., verify=...)`）——不翻 J5 分支、J6 以外不得更远、
   **进出两段都要过 `_joint_move`**。原来的兜底只挑"J6 更小"的解，可能用 120° 的 J1 去换 130° 的腕转，
   而且只验进入、不验离开。

两条读数字时必须记住的口径：

- `literal_*` 只统计 `J` 指令段。`_arrival` 改成直线之后，大部分过渡段变成 `L`，
  `literal_total_deg` 会掉到 ~35°——**前后对比要用 `physical_total_deg`**，否则会得出"J6 突然变好了"的错觉。
- 出厂配置 `robot.enabled: false`，命令行默认这四道闸只是"记录下来的意图"；**网页端强制开门**
  （关节筛选没有开关），所以页面跑的每一次都吃这四把闸。

**仍未解决**：`banded` 模式最坏单次 J6 换向 **132.4°**（`standard` 是 48.6°）。原因是倾斜带的朝向更杂，
而排序的 J6 计价只在 `tidy` 档开着。下一步先试把 `order_j6_weight_mm_per_deg` 从 10 提到 20，
再决定要不要给 `banded` 单独设一条 J6 上限。

#### 二、扫描带配置：一族种子从来没出过货

现场看到的不对称（一侧成片扫描带、另一侧孤立停点）不是参数没调，是一个**符号写错**：

```python
# 改之前：-tilt_axis(-normal, tangent*sign, tilt)
#   tilt_axis(inward, t, tilt) 本来就是"从内法向朝 t 倾 tilt"，
#   前面再加负号等于倾到 180−tilt，也就是 135°——光轴朝零件背面
```

实测 `-dot(axis, normal) = -0.707`（入射余弦 −0.707），所以**每个倾斜种子在第一次延伸就被
`_reaches_any` 判死**，这一族自上线以来产出的带是 **0 条**。正对的梯子够得着平板，够不着立着的侧壁
和压钳下的翻边——唯一能斜着够到的那族是死的，于是那些区域只能退化成"停在那儿拍一张"。
改成 `tilt_axis(inward, …)`（45°）之后这族才开始出带：修复前它一条带都没有，修复后同工位同参数下
`standard` 档整个工位是 37 条候选带，`banded` 档 281 条（后者同时把播种铺满一圈、间距压到 60 mm，
两者不能拆开算账）。

新增 `stroke.plan_mode`（`standard` / `banded`，`config.plan_preset` 展开），一次捆三件必须一起动的事：

| 档 | 倾斜种子族 | 关节包络 | 一条带的价 |
|---|---|---|---|
| `standard`（出厂） | 1 个方位（2 个轴向）、每 200 mm 一颗 | `joint_span_fraction 0.9` + `joint_margin_deg 5` | 2.0 |
| `banded`（扫掠优先） | 3 个方位（6 个轴向、每 60°）、每 60 mm 一颗，只铺偏离主方向 ≥45° 的墙/翻边，上限 96 颗均匀抽稀 | `1.0` / `0`（用满控制器限位，不再自设舒适区） | 1.0 |

为什么不拆成三个开关：单独动任何一个都量不出差异——种子铺了但包络缩着，`gate_ok` 是**整条带**判死
（缩包络下 43 条候选带 vs 放开 216 条）；包络放开但种子没铺，没东西可长；带价还是 2.0，短于两个视场
的带会输给盖住同样面积的两个停点。所以合成一个模式，并且与 `route_style` 正交（一个决定"选什么"，
一个决定"怎么连"）。

同工位、10 mm 网格、99% 目标、`tidy` 的实测：

| | `standard` | `banded` |
|---|---|---|
| 长出来的候选带 | 37 | **281** |
| 交付 带 / 停点 | 5 / 18 | **11 / 3** |
| 点数 | 31 | **27** |
| 关节换向中断 | 21 | **13** |
| 覆盖率 | 99.03% | 99.04% |
| 候选池上限 | 99.42% | **99.62%** |
| 最小姿态余量 | 5.37° | 0.03° |
| 最坏单次 J6 | 48.6° | 132.4° |

代价与边界，写在这里免得下次当成 bug：

- 包络用满 = 余量 0°，也就是**贴着控制器限位跑**；位姿仍在软限位内、仍避开 J5 奇异，
  是"不额外自设舒适区"，不是"忽略限位"。
- 无上限的稠密种子跑不完（20 分钟没出结果），所以 `banded` 加了 45° 墙过滤和 96 颗上限；
  抽稀是**均匀步进**而不是取前 N 颗，否则只铺满第一个角。
- `standard` 仍是出厂值与回归基准；**两档的点数与覆盖率不能互相作为回归基准**。
  但要记住：符号修复对 `standard` 也生效，所以 `standard` 的输出**不再是 2026-11-01 之前的逐字节旧行为**
  （配置值一个字没改，变的是死族变活）。做回归对比请拿修复之后的基线。
- 倾斜扫掠的阴影代价是真的：同一块面积上斜着扫的数据不如正对扫。这一族的存在意义是
  "盖住别的办法盖不到的"，不是去竞争。

#### 三、网页端：六项配置收进「高级配置」

`交付模式 / 规划速度 / 规划模式 / 路线风格 / 覆盖率目标 / 扫描带角价` 收进一个默认折叠的面板，
收起时标题右侧一行小字写清当前配方（由控件本身推出来，不另写文案）。

起点值走服务端 `/api/config` 的 `defaults`（`scanweb.SITE_DEFAULTS`：扫掠 / 快速 / 扫掠优先 / 整齐 /
99% / 2.0），**故意不写进配置文件**：配置文件里的出厂值是命令行与回归基准的参照，改它会让
`--plan-mode standard` 名不副实。两者分开，"页面默认什么"与"命令行默认什么"各说各的，都写清楚。

这六项随「方案」一起保存和读取——重启程序后一键恢复模型、定位点和坐标时，配方跟着一起回来，
否则同一个零件重启后会按另一套参数重跑，而报告里看不出差别在哪。

# FANUC 扫描工位：扫描视点自动规划

针对**冲压薄板零件**，在搭载 **TrackScan-Sharp 49** 光学扫描仪的 FANUC 机器人上，
自动生成**扫描头视点**。

输入工位数模（零件、夹具、底座、光学跟踪器）与扫描仪参数，输出一组扫描头位姿
（位置 + 光轴 + 滚转），使其共同覆盖零件需要测量的那一面；并导出为 FANUC `.LS`
程序，供现场在 ROBOGUIDE 中校验可达性。

> **状态：规划器已实现，尚未拿到现场实测参数。**
> [`src/scanplan/`](src/scanplan) 下的各个模块均可单独测试，端到端跑通，
> 并在**真实工位数模**上复现了可行性验证的结论（见下节）。
> 扫描仪参数仍是**占位值**，所以覆盖率数字只能当**指示性**参考。
> 这些约束背后的设计笔记为私密保存，因为其中含客户零件尺寸。

## 它做什么

1. **工位建模** —— 载入零件、夹具、底座与跟踪器，统一到同一 CAD 坐标系；对齐过程
   显式且带自检，不盲信数模文件。
2. **目标面分割** —— 按**拓扑**把零件分成"原始平整铁皮的两个面"，采样待测的那一面
   （见下节）。
3. **生成候选视点** —— 围绕目标面生成候选位姿，逐条判定视场、量程、入射角、遮挡、
   扫描头能否放得下、以及跟踪器是否看得见。
4. **选取最小覆盖集** —— 在满足覆盖率前提下选出最少的视点。
5. **（默认）把视点连成扫描带** —— 现场是**一路扫过去**，不是"停稳再拍"。
   `stroke.enabled` 打开时，规划单元从孤立位姿变成"直线段 + 恒定姿态"，覆盖按整段扫掠计算，
   输出是一条带过渡段的连续路径（`L ... CNT0`）。**这是默认模式**；网页端「交付模式」可以在
   它和「纯位姿模式（旧版）」之间切换，纯位姿模式的结果与只有位姿时逐项一致。理由与实测数字
   见下面"连续路径在真实工位上的第一次实测"，或（私密、不入库的）设计文档《连续路径扫描》第 12 节。
6. **导出** —— 视点集、覆盖报告、一个自包含的 3D 视图，以及 FANUC `.LS` 程序与其帧契约。

## 它明确不做

逆解、关节限位、机器人碰撞、运动时间优化。导出的 `.LS` **只含笛卡尔位姿**，由控制器 /
ROBOGUIDE 求解。这也是本方案不需要机器人模型的原因，以及为什么交付物是视点集而不是
机器人程序。

## 目标面：拓扑定义

零件是一块冲压出来的薄铁片，所以按广义的面来说它**只有两个面**——就是它还是平整铁皮时
的两个表面。成型侧壁属于它由哪一面折出来就归哪一面。冲裁（冲孔/落料）出来的剪切断面
**两个面都不属于**，因为它是"切开材料"产生的，不是铁皮的表面。

```
目标 = 原始铁皮的两个面之一
       **含**成型侧壁、含凹腔/凹槽内壁
 减去 = 夹具夹持的区域（不要求测量）
排除 = 剪切断面（冲裁/冲孔边）
排除 = 铁皮的另一面
```

基于朝向的规则在这里**全都行不通**，原因各不相同：`normal_z > 0` 在零件于夹具中倾斜时
立刻失效；二面角分割出的 patch 不等于一个面，因为折痕会把一个面切成好几块平面；用
"与零件自身贯穿轴的夹角阈值"会把成型侧壁切掉，而侧壁属于该面；而"去掉冲裁边后取连通
分量"在真实 CAD 网格上直接失败——各张曲面是分别网格化的，重合顶点从未合并。

有效的方法记录在 [`src/scanplan/sheet_split.py`](src/scanplan/sheet_split.py)。

## 快速开始

需要 Python 3.10 与 [uv](https://docs.astral.sh/uv/)。

```bash
uv sync --extra dev --extra embree
uv run pytest
```

`embree` 是可选项，但强烈建议装：它把光线求交加速约三个数量级，直接决定真实零件
"能不能在可接受时间内算完"。

只有一个入口：

```bash
uv run scanplan plan --station input/<工位>.json \
                     --face auto --out output/<零件>/

uv run scanplan ls   --viewpoints output/<零件>/viewpoints.json \
                     --prog-name PART01 --out output/<零件>/

uv run scanplan view --viewpoints output/<零件>/viewpoints.json \
                     --station input/<工位>.json --out output/<零件>/
```

`--station` 给出三个数模的路径与它们的配准变换；也可以直接给
`--part/--fixture/--base` 三个路径，此时按单位变换处理。可以加的还有
`--config`（覆盖配置）、`--tracker x,y,z`（给出跟踪器真实位姿）、
`--tracker-sweep`（不给位姿时，报告 192 个候选摆位的差别）、`--no-3d`（不写 3D 视图）、
`--max-faces`（3D 视图里每个模型的显示面数上限）、`--quiet`。
模板见 [`configs/station.example.json`](configs/station.example.json)。

> **`--face upper` / `--face lower` 是几何名，不是物理名。** 哪一个面叫"上面"取决于
> 分面时定向种子的符号，而那个符号并没有锚定到工位文件上：交换它，两个面的名字会互换，
> 而两面面积、料厚、定向比例**全都一模一样**。报告里因此记录了 `through_axis`（分面认为
> 的"厚度方向"）和一段说明，供人核对。**默认的 `--face auto` 不受影响**，它两面各算一次
> 可达性、取高的那一面，这也是推荐用法。

`plan` 与 `.LS` 导出**刻意分开**：ROBOGUIDE 的坐标系契约（用哪个 `UFRAME`、原点落在
哪里）需要与现场商定，可能只要求重新导出而不必重跑规划。所以 `ls` 只读视点文件，
**不需要数模**。

现场可用零件上的三个定位基准点，把 CAD 路径配准到实测的机器人基坐标系。每个基准点必须提供一对
坐标：CAD/视点文件坐标中的点，以及现场在机器人基坐标系中测得的点（mm）。
如果 CAD 中的对应特征还没有坐标，可以先在模型视图中点选，再输入三组现场测量值。
下面示例中现场坐标来自机器人基坐标：

```bash
uv run scanplan pick-datums --station input/<工位>.json \
  --measured-points "x1,y1,z1;x2,y2,z2;x3,y3,z3" \
  --coordinate-system robot_base_mm \
  --out output/<零件>/registration_picked.json
```

窗口中按 P1、P2、P3 的顺序点击 CAD 上同一物理基准特征，并确保顺序与测量坐标一一对应；
视图按所选的整车坐标轴正负方向投射到模型，右键可以撤销上一个选择。若已有配准文件，可用
`--guide-registration` 将其中的 CAD 点显示为青色参考标记；仍需在窗口中逐点点击，点击标记
附近（30 mm 内）会吸附到原 CAD 点，其他位置则按表面射线拾取。点选完会输出配准 JSON，
并打印拟合误差。三对点也可以直接写入 JSON：

```json
{
  "coordinate_system": "robot_base_mm",
  "point_pairs": [
    {"cad_mm": [100.0, 200.0, 300.0], "robot_base_mm": [510.0, 220.0, 840.0]},
    {"cad_mm": [200.0, 200.0, 300.0], "robot_base_mm": [510.0, 320.0, 840.0]},
    {"cad_mm": [100.0, 280.0, 300.0], "robot_base_mm": [430.0, 220.0, 840.0]}
  ]
}
```

需要重用已有 CAD 点作为拾取参考时，可添加 `--guide-registration`：

```bash
uv run scanplan pick-datums --station input/<工位>.json \
  --measured-points "x1,y1,z1;x2,y2,z2;x3,y3,z3" \
  --coordinate-system robot_base_mm \
  --guide-registration input/previous_registration.json \
  --out output/<零件>/registration_picked.json
```

配准输入只接受机器人基坐标：`coordinate_system` 必须是 `"robot_base_mm"`，配对字段名必须是
`robot_base_mm`；也兼容 `measured_coordinate_frame: "robot base"` 配合 `cad_points_mm`、
`measured_points_mm` 这种数组格式。写成 `UFRAME 1`–`UFRAME 9` 的配准文件会被拒绝并提示
用基坐标重新量点——现场用 UFRAME 量点时请改用浏览器界面（`scanplan web`），那里可以直接
选择机器人基坐标或 `UFRAME 1`–`UFRAME 9`。

```bash
uv run scanplan ls --viewpoints output/<零件>/viewpoints.json \
                   --prog-name PART01 \
                   --registration input/part_registration.json \
                   --out output/<零件>_现场配准/
```

默认要求三个点的最大配准残差不超过 3 mm；可按测量精度用
`--max-registration-error-mm` 调整。输出 `registration_report.json`，记录刚体变换和各点误差。
三个定位点必须不共线、对应同一组 CAD 特征，且现场坐标必须是机器人基坐标，不能与其他
坐标系混用。程序因此固定使用 `UFRAME 0`；导出后仍须在 ROBOGUIDE/现场核对点位。

### 本机浏览器工位界面

```powershell
uv run scanplan web
```

浏览器访问 `http://127.0.0.1:8765`。界面可导入零件与夹具 STL（底座可选；未导入时服务会
自动生成一块位于零件下方的参考平板），导入后在可旋转、缩放的 3D 模型上依次点选 3 个或
4 个定位点，再填写与它们对应的现场坐标。每对点按相同序号配对，三点或四点到齐后自动计算
并显示从整车 CAD 坐标到所选机器人坐标系的安装平移和旋转矩阵。配准最大误差限值默认为
50 mm，超过该限值时拒绝输出。

扫描面按整车坐标 ±X/±Y/±Z 选择，也可根据模型主平整面面积自动推荐，或直接在模型上点选
表面。**交付模式**有「扫掠模式 · 连续扫描带」（默认）和「纯位姿模式（旧版）」两种：前者把
相邻视点连成扫描带，覆盖率描述的是真正扫过的区域，`.LS` 用 `L` 直线 + `CNT0` 连续走；后者
与旧版一致，只交孤立位姿、不承诺点间运动，`.LS` 用 `J` + `FINE`。确认安装姿态与扫描面后，
按所选方向分割目标面、运行路径规划并生成 FANUC `.LS`。
LS 程序名可在界面中自行命名；规划完成后页面显示覆盖率、视点数、目标采样点和漏扫点，
并可选择在零件 3D 模型上叠加显示扫描路径。结果与工位设置在同一页面，可直接下载
`.LS`、帧契约、规划报告、
覆盖报告等文件，也可一键跳转到 `viewer.html` 做逐视点、逐采样的可视化分析。所有 STL
和输出都只在本机处理，不发送到外部服务。

路径规划使用本次界面导入的零件 STL，生成前同步覆盖项目 `input/part.stl`，同时将相同的
STL 副本保存为该次运行目录中的 `part.stl` 并应用配准变换；不会使用其他运行遗留的
零件模型。模型视图中可按鼠标右键或按钮撤销最后一个 CAD 选点。

整车轴向固定为 X 前负后正、Y 左负右正、Z 下负上正。浏览器工具生成的路径仍需在
ROBOGUIDE 核实 UFRAME/UTOOL、可达性与碰撞；它不替代机器人仿真和现场安全确认。

### 交付物

`plan` 在输出目录写下八个文件（`--no-3d` 时六个）：

| 文件 | 内容 |
|---|---|
| `viewpoints.json` | 视点集：位置 + 光轴 + 滚转 + 覆盖点数/面积 + 入射角 + `tracker_ok` + 来源，以及程序顺序 `order` / 所属带 `stroke_id` / 角色 `role` |
| `viewpoints.csv` | 同一份数据，便于 Excel 目视 |
| `exempt_points.csv` | 被夹持区豁免的点云（供人工核对 CAD 夹持区与实物是否一致） |
| `unreachable_points.csv` | 漏扫点云，**每点带原因**（`blocked_by_part` / `blocked_by_fixture` / `blocked_by_base` / `blocked_by_tracker` / `never_in_view` / `only_poses_that_collide`） |
| `coverage_report.json` | 覆盖报告：覆盖率、视点数、入射角分布、漏扫聚类、参数出处（数据表 / 推导 / 未实测）、路径与中断统计、以及**它没有建模什么** |
| `summary.txt` | 上面那些数字的人读版本 |
| `viewpoints_3d.html` | **单文件 3D 视图**：零件/夹具/底座 + 视点位置、光轴与视场锥 + 已覆盖/未覆盖采样 + 程序路径与回放 |
| `target_samples.npz` | 采样点 + 逐点覆盖位掩码，供 3D 视图回答“哪些视点能扫到这个点”；`scanplan view` 重新渲染时读它 |
| `strokes.json` | **只在扫描带模式下**：程序顺序的权威来源，每条带的端点、姿态、覆盖贡献与角色 |

`ls` 写下 `.LS` + `_points.csv` + `_frame.json`（帧契约）。视点文件里带 `stroke_id`
时，`ls` **固定用配置里的 `L <速度> CNT0` 并按文件顺序下发**，并拒绝任何重排请求：
重排会把一条带的两端拆成两次互不相关的移动，而覆盖率是对那条整带算的。

### 3D 视图

`viewpoints_3d.html` 是**一个文件，没有外部依赖，也不联网**：网格、采样点和视点集都以
base64 缓冲区嵌在页面里，用页面自带的小型 WebGL 渲染器画出来。现场那台只看图纸的电脑
只要能开浏览器就能看，引用 CDN 的页面在那里只会是一片空白。

页面里可以左键拖动旋转、滚轮缩放、右键或 Shift 拖动平移，单击视点看它的坐标、入射角、
覆盖面积与来源；右上角可以逐层关掉零件、夹具、底座、视场锥和采样点。

**视场锥**默认只画选中那一个，因为一百多个视点同时铺开时上千条线会糊成一片。右上角
的下拉框可以切换：`仅选中`（默认）、`全部`（只画各视点在工作面上的矩形，淡色）或
`关闭`。想核对某处是否真的被扫到，就单击那里的视点方块，看它的锥落在零件的什么位置。

**采样点**同样是一个下拉框：`全部`（已覆盖绿 / 未覆盖红）、`仅选中视点`（只留该位姿能
测到的点）、`仅未覆盖`、`关闭`。**单击零件上的任一点**，右侧会给出该点的位置、是否被
覆盖，以及**哪些视点能扫到它**——这些视点会在三维视图里高亮成青色，点列表里的编号即可
直接切过去看它的视场。未覆盖的点会明确写“没有视点能扫到”。

**扫描路径与回放**（带式计划尤其需要）：交付点按程序顺序连成路径，同一 `stroke_id` 内
两端相连的那一段画成亮色（这一段是真在扫），其余过渡、退刀、转向段画成暗灰。单击任意
一段路径即从该处开始回放：扫描头沿路径移动，视场矩形按两端位姿插值，已扫过的采样点按
“首次被覆盖的路径点”依次点亮——扫描区域就是这样一段段长出来的。右上角面板提供
▶/⏸、复位、0.5–4× 速度、进度条，以及**镜头跟随**（视角跟着扫描头走，便于贴着零件看
局部）。回放依赖 `target_samples.npz` 里的覆盖关系；旧运行缺这个文件时，路径与位姿照样
回放，只是不会点亮采样。

这一层“谁看见了谁”的关系来自 `plan` 同时写下的 `target_samples.npz`（采样点 + 逐点
覆盖位掩码，约 1.6 MB）。`scanplan view` 会读它，所以重新渲染也能保留采样点与查询能力；
如果旧目录里没有这个文件，页面会照常打开，只是不显示采样点。

这一切都在与规划器分开的包里：[`src/scanview/`](src/scanview)——`payload.py` 负责把
数模/采样/视点编码成页面数据，`viewer.html` 是页面自带的渲染器。它只从 `scanplan`
取扫描头坐标系（`scanner_frame`）和视场尺寸，保证图与导出的位姿契约不会各说各话；
`scanplan` 这侧只有两个调用点（`plan` 写页面、`view` 重渲染），算法本身不依赖它。

视点的画法**与规划器共用同一套定义**：位置就是扫描头的测量参考点，视线沿光轴延伸一个
工作距离，末端是按 `scanner_frame` + 滚转摆出的矩形视场。因此这张图不会和导出的位姿
契约各说各话。

`plan` 总是同时写出这张图；`view` 只读 `viewpoints.json` 与数模重新渲染，**不需要重跑
规划**，用于改了配色、想换个角度看、或换台电脑放给评审看。`--max-faces` 控制每个模型
的显示预算，超出的模型才做顶点聚类抽稀——薄板零件抽狠了会把正反两面焊在一起，所以
默认值远高于真实零件的面数。

### 帧契约（**交付物的语义，不是细节**）

- 视点的 `position` 是扫描头的**测量参考点**（覆盖率计算里那个"距目标点一个工作距离"
  的点），单位 mm，坐标在**数模坐标系**里；
- 局部 **+Z 就是光轴**，从扫描头**指向零件**；
- `.LS` 里的点位是**笛卡尔位姿**，为了对齐这个契约，ROBOGUIDE 侧的 **UTOOL 必须按这个
  参考点教**。教错 → 所有点位的实际测量距离整体偏掉一个常数，仿真里看不出来，实机上
  是系统性误差。

坐标系口径有两条路：把 `UFRAME 1` 教到数模原点（底座固定，只需教一次），或用
`--place "x,y,z,w,p,r"` 把数模摆进 ROBOGUIDE 世界（此时程序用 `UFRAME 0`）。
**无论哪条，都必须先在 ROBOGUIDE 里确认点位落在零件上**，再谈可达性。

### 工位数模

把零件、夹具、底座的 CAD 放进 `input/`，并保证它不进版本控制——那是客户几何。
如果数模是**逐个文件导出**的 IGES，装配位姿会丢失，所以工位建模里包含一个显式、
带自检的对齐步骤，而不是直接信任文件。

## 配置

[`configs/scanner_trackscan49.json`](configs/scanner_trackscan49.json) 存放扫描仪参数。
参数的出处分四档，文件里的注释与报告里的 `parameter_provenance` 按同一套分档写：
**数据表直接给出**（基准距、景深、最大面幅、跟踪距离）、**由数据表推导**（量程、
跟踪器半角 25°）、**仍未实测**（入射角上限、扫描头外形包络、视场锚点距离、标记点朝向）、
**设计取值**（距离/倾角/滚转阶梯、扫描带步长）。读覆盖率数字之前先看**仍未实测**那一档：
`max_incidence_deg` 的敏感度远高于其他任何一项，而 `fov_anchor_distance_mm` 一动就会
让视点数变两成。

[`configs/stroke_on.json`](configs/stroke_on.json) 现在只是把扫描带（连续路径）**显式钉住**：
它已经是默认值，这份覆盖件留着是为了让引用它的脚本在默认值再变时仍然表达同一个意思。

## 目前的验证情况

在**真实工位数模**上跑过两轮，结论与设计阶段的四轮可行性验证一致：

| 检查项 | 设计阶段（8 mm 网格） | 本次实现复跑（8 mm） |
|---|---|---|
| 上面面积 | 1.0544 m² | **1.0544 m²** |
| 下面面积 | 1.0511 m² | **1.0511 m²** |
| 剪切断面 | 0.0117 m² | **0.0118 m²** |
| 镜像对面命中率 | 99.1% | **99.1%** |
| 定向种子 / 传播 | 88.9% / 99.4%（9 轮） | **88.9% / 99.4%（9 轮）** |
| 料厚（中位） | 0.698 mm | 0.678 mm（光线起点偏置 0.02 mm 所致） |
| 覆盖率 | 99.10% | 99.48%（同一张面、不同抽样，见下） |
| 视点数 | 50 | **50** |

> **覆盖率那一行的 0.38 个百分点不是算法差异，是抽样差异。** 两条依据：
> 一是本实现复刻了第四轮的候选阶梯（同一份配置、逐项相同），两者算出的
> 覆盖率完全一致；二是把**第四轮报告里自己的 154 个漏点**拿来，用本实现的
> 判定规则和一份**逐行照抄的第四轮规则**分别过一遍（同点位、同法线、同求交
> 器）：154 个点的结论**逐点一致，0 处分歧**。差异来自抽样：第四轮抽到的是
> 17033 个点，本次是 16937 个，两套点不是同一批（第四轮的漏点距本次最近的采样
> 点中位 3.32 mm）；而 8 mm 网格下"成型侧壁"那种 1–2 mm 宽的特征上谁被抽中、
> 谁被留下，本身就是抽签。设计 §9.3 记的是同一件事：未播种时同一个输入，覆盖率
> 在 **99.10%–99.48%** 之间跳。本实现三次播种（7/11/13）得 99.48/99.52/99.55%，
> 波动集中在 `never_in_view`（31/17/16），其余成因稳定。
>
> 结论：**把覆盖率当"约 99.5% ±0.1"读，不要追第三位小数**，也没必要为了对上
> 第四轮那个数去改判定规则。

有两条结论影响了设计，也在复跑中重现：

- **固定的单台跟踪器本身不构成瓶颈**，前提是它沿**零件薄轴**方向架设，而不是正对大面
  看过去——机理是零件本体挡住了**扫描头**，不是跟踪器视场角不够；
- 残余漏扫是**二十来处小特征**（窄槽、小凹坑内壁），而不是一整片够不到的区域。

在**交付默认口径**（3 mm 采样网格 + 由粗到细补候选 + `--face auto`）上：

| | 上面（`auto` 选中的） | 下面（对照） |
|---|---|---|
| 贪心集合覆盖后 | 99.50%（103 点） | 91.29%（107 点） |
| 补一轮候选后 | **99.71%（111 点）** | 96.66%（140 点） |
| 补第二轮后 | 99.71%（117 点，只多盖 5 个采样点，第三轮不再获准） | 96.77%（146 点） |

两件事因此有了实测依据：

- **收益在候选密度，不在选择算法**：补一轮把上限抬了 0.21 个百分点（上面），下面抬了
  5.4 个百分点。集合覆盖本身早就把"池子够得着的地方"全盖住了，所以"补齐"那一阶段在
  实测里是空的——**视点数是被候选生成限制的**。
- **"哪一面朝上"的自动判定**用两面各算一次可达性来做：上面 99.71% vs 下面 96.77%，
  差距明显，与设计阶段的结论一致。

一个**取舍**留在这里，因为它是"覆盖率优先"这条排序规则的必然结果：第二轮补候选只多盖了
5 个采样点（119480 中的 0.004%，约 44 mm²），却多要 6 个视点。实现按"先比覆盖率、再比视点
数"取舍，所以留下了 117 点这一版。不想为千分之几个点付 6 个位姿的场合，可以把
`refine_rounds` 设成 1。

这些数字依赖占位的 `max_incidence_deg`，只能当**指示性**参考，因此这里刻意不写出具体数值。
抽样本身还会带来几个千分点的波动（见上一节的说明），所以**报覆盖率请带"约"字**。

### 连续路径（扫描带）在真实工位上的第一次实测

> **已被下一节取代。** 这一轮的数字有一个记账缺陷（选中的位姿没进程序却算了覆盖率），
> 下面的"点数没有降到 ≲70"是那个缺陷的后果，不是曲面的硬限制。

同一台机器、同一份代码、`face=auto`、跟踪器未给位姿，位姿方案与扫描带方案各跑一次：

| | 上面板（`auto` 选中的） | 下面板（对照） |
|---|---|---|
| 位姿方案 | 99.70% / 102 点 | 97.06% / 155 点 |
| 扫描带方案 | **99.74% / 114 点** | **97.46% / 134 点** |
| 规划耗时 | 293 s | 772 s（2.63×，设计允许 ≤3×） |

三件事要说清楚：

- **覆盖率没有降，两个面都升**，而且带方案里"承诺覆盖"等于"路径真的扫过的覆盖"，
  中间没有未定义的运动；位姿方案的点与点之间现场还得自己走。
- **点数没有像设计期望的那样降到 ≲70。** 恒定姿态是硬约束：在本曲面上，一条带能一直
  满足六条判据的长度往往只有 200–400 mm，于是一条带只换掉 2–3 个位姿，而它自己要付
  2 个端点 + 2 个过渡点。上面板因此多了 12 个点，下面板少了 21 个点。要真正降点数，
  得动用设计 §4.3 后置的栅格直扫（G2），这次没做。
- 报告里仍可能有一条 `constraint_violation`（某个过渡段在最大抬升下仍差 ~1 cm 间隙）。
  它被**写进报告**而不是被修掉，因为再往上抬会走近背后的底座。

扫描带**默认开启**；要回到旧行为（只交位姿、不承诺点间运动），网页端选「纯位姿模式（旧版）」，
或用 `configs/lean.json`，或把 `stroke.enabled` 关掉——那与 v1 逐项一致。之所以要在默认口径
下谨慎读点数：P0 的三项标定（视场锚点、入射角上限、扫描头包络）还没做，而这个未标定的量能
直接让点数变两成。

### 点数骤减：以可接受覆盖率换取路径点数量（2026-10-20）

上一节那张表有一个**记账缺陷**后来被查出来了：选中但没被交进路径的位姿仍然算进了覆盖率。
上面板报告的 99.741%，交付出去的 29 条带实际只扫到 **91.98%**，差的那部分是 97 个从未出现在
程序里的位姿。

修掉之后，再加上"目标停止 + 转角计价 + 轴加权 + 连接段压缩"四项改动，同一台机器、同一张面：

| 运行 | 覆盖率目标 | 点数 | 路径实扫 | 再定向 | 耗时 |
|---|---|---|---|---|---|
| 旧扫描带方案 | 跑到耗尽 | 114 | 91.98%（报告 99.74%） | 26 | 772 s |
| `path` 模式 | 97% | **20** | 97.77% | 7 | 434 s |
| `path` 模式 | 99% | **31** | 99.07% | 10 | 393 s |
| `lean` 模式 | 99% | **29** | 未校核 | — | ~200 s |

- 覆盖率阈值是**现场旋钮**：`scanplan plan ... --coverage-target 97.5`（或 `none` 表示跑到耗尽），
  也可以写进配置文件的 `target.coverage_target_pct`。默认 99.0。
- `path`（默认）把每个交付点之间的运动都过一遍间隙与旋转速率校核；`lean` 交出位姿、不承诺
  点间运动，与今天的 v1 同级——在 99% 档它只比 `path` 少 2 个点。
- 报告里的 `coverage_pct` 现在**等于**路径里所有覆盖点的并集（有一条测试守着这个不变量），
  `swept_coverage_pct` 另外算上过渡段顺手扫到的面积，只作参考、不参与验收。

| 配置档 | 用途 |
|---|---|
| [`configs/stroke_on.json`](configs/stroke_on.json) | 扫描带（现在就是默认，这份用于显式钉住） |
| [`configs/lean.json`](configs/lean.json) | 位姿优先、不生成连接点 |
| [`configs/legacy_exhaust.json`](configs/legacy_exhaust.json) | 复现旧口径（毫米计价、L2 连接、跑到耗尽） |

### 工位自检在真实数模上报出来的问题

`plan` 每次都先跑一遍工位自检：三套数模是不是真的按工位文件说的那样坐在一起。在真实工位
数模上它报出的是：

> 零件有 **16 个网格点**钻进了夹具内部，最深约 **1.7 mm**（最深点坐标、探针点数与判定依据都写在
> `output/*/coverage_report.json` 的 `alignment_checks` 里，那一层是 gitignore 的）。

这与设计 §4.3 的怀疑一致——**夹具数模是设计版，现场实际夹持区不同**——所以要现场确认夹具
到底压在哪里、是否真的与零件干涉。设计 §4.1.2 当时自检的结论是"无干涉，最小面间距
0.204 mm"，但那个判据是面到面的距离，**看不见几毫米的穿透**；本实现改成有符号判据（零件
表面点落在夹具表面之后，且对附近每一片夹具表面都成立）。

这个判据现在是**确定性的**：它走两套数模自己的几何（零件的顶点与面心，再加按预算铺的面内
格点），一个随机数都不抽，所以换种子答案不变。两处仍然看不见的情况写在
[`scene.py`](src/scanplan/scene.py) 的注释里：整块零件完全埋在夹具体内，以及夹具网格法线
整体反号。

## 报告里必须一起读的三条声明

覆盖面**只是几何可达性**。报告里会显式写明下面三件事，任何引用覆盖率数字的场合都应带上：

1. **不含机器人可达性**：逆解、关节限位、机器人碰撞由现场在 ROBOGUIDE 里判，所以交付的
   `.LS` **可能包含 ROBOGUIDE 判为不可达的点位**——这是预期，不是缺陷。ROBOGUIDE 报
   不可达时**先换 `CONFIG` 构型再试**。
2. **不含机械臂对跟踪器的遮挡**：本阶段没有机器人模型，`tracker_ok` 只对零件/夹具/底座
   判遮挡。现场架设时请同时避开机械臂的常态工作扇区。
3. **哪些参数还是占位值**：报告逐条列出，`max_incidence_deg` 排在最前。

## 原管线与 `.LS` 写入器的关系

[`reference/`](reference) 冻结保留原管线：`PHASE_1`～`PHASE_6`、集合覆盖求解器、以及
IGES→网格转换器。它作为回归基线保留，同时也是新规划器**移植**（而非重写）FANUC `.LS`
写入器的来源——那个写入器已经解决了 FANUC ASCII 格式里一堆繁琐且不容出错的地方
（固定轴 XYZ 欧拉角、万向锁分支、`/ATTR` 自洽、无前导零的数字格式、程序名合法化）。
手册见 [`reference/MANUAL.md`](reference/MANUAL.md)。

**本路线不使用 `PHASE_3` / `PHASE_4` / `PHASE_5`**：它们是 UR5e 逆向运动学与机器人基座
采样、TSP 排序那一层，而本方案整层移除了（见"它明确不做"）。代码没动，只作参考。

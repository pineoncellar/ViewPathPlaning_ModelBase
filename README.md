# FANUC 扫描工位：扫描视点自动规划

针对**冲压薄板零件**，在搭载 **TrackScan-Sharp 49** 光学扫描仪的 FANUC 机器人上，
自动生成**扫描头视点**。

输入工位数模（零件、夹具、底座、光学跟踪器）与扫描仪参数，输出一组扫描头位姿
（位置 + 光轴 + 滚转），使其共同覆盖零件需要测量的那一面；并导出为 FANUC `.LS`
程序，供现场在 ROBOGUIDE 中校验可达性。

> **状态：规划器已实现，尚未拿到现场实测参数。**
> [`src/scanplan/`](src/scanplan) 下的各个模块均可单独测试，端到端跑通，
> 并在**真实工位数模**上复现了可行性验证的结论（见下节）。
> 扫描仪参数仍是**占位值**，所以覆盖率数字只能当**指示性**参考。
> 这些约束背后的设计笔记为私密保存，因为其中含客户零件尺寸。

## 它做什么

1. **工位建模** —— 载入零件、夹具、底座与跟踪器，统一到同一 CAD 坐标系；对齐过程
   显式且带自检，不盲信数模文件。
2. **目标面分割** —— 按**拓扑**把零件分成"原始平整铁皮的两个面"，采样待测的那一面
   （见下节）。
3. **生成候选视点** —— 围绕目标面生成候选位姿，逐条判定视场、量程、入射角、遮挡、
   扫描头能否放得下、以及跟踪器是否看得见。
4. **选取最小覆盖集** —— 在满足覆盖率前提下选出最少的视点。
5. **导出** —— 视点集、覆盖报告，以及 FANUC `.LS` 程序与其帧契约。

## 它明确不做

逆解、关节限位、机器人碰撞、视点排序、运动时间优化。导出的 `.LS` **只含笛卡尔位姿**，
由控制器 / ROBOGUIDE 求解。这也是本方案不需要机器人模型的原因，以及为什么交付物是
视点集而不是机器人程序。

## 目标面：拓扑定义

零件是一块冲压出来的薄铁片，所以按广义的面来说它**只有两个面**——就是它还是平整铁皮时
的两个表面。成型侧壁属于它由哪一面折出来就归哪一面。冲裁（冲孔/落料）出来的剪切断面
**两个面都不属于**，因为它是"切开材料"产生的，不是铁皮的表面。

```
目标 = 原始铁皮的两个面之一
       **含**成型侧壁、含凹腔/凹槽内壁
 减去 = 夹具夹持的区域（不要求测量）
排除 = 剪切断面（冲裁/冲孔边）
排除 = 铁皮的另一面
```

基于朝向的规则在这里**全都行不通**，原因各不相同：`normal_z > 0` 在零件于夹具中倾斜时
立刻失效；二面角分割出的 patch 不等于一个面，因为折痕会把一个面切成好几块平面；用
"与零件自身贯穿轴的夹角阈值"会把成型侧壁切掉，而侧壁属于该面；而"去掉冲裁边后取连通
分量"在真实 CAD 网格上直接失败——各张曲面是分别网格化的，重合顶点从未合并。

有效的方法记录在 [`src/scanplan/sheet_split.py`](src/scanplan/sheet_split.py)。

## 快速开始

需要 Python 3.10 与 [uv](https://docs.astral.sh/uv/)。

```bash
uv sync --extra dev --extra embree
uv run pytest
```

`embree` 是可选项，但强烈建议装：它把光线求交加速约三个数量级，直接决定真实零件
"能不能在可接受时间内算完"。

只有一个入口：

```bash
uv run scanplan plan --station input/<工位>.json \
                     --face auto --out output/<零件>/

uv run scanplan ls   --viewpoints output/<零件>/viewpoints.json \
                     --prog-name PART01 --out output/<零件>/
```

`--station` 给出三个数模的路径与它们的配准变换；也可以直接给
`--part/--fixture/--base` 三个路径，此时按单位变换处理。可以加的还有
`--config`（覆盖配置）、`--tracker x,y,z`（给出跟踪器真实位姿）、
`--tracker-sweep`（不给位姿时，报告 192 个候选摆位的差别）、`--quiet`。
模板见 [`configs/station.example.json`](configs/station.example.json)。

> **`--face upper` / `--face lower` 是几何名，不是物理名。** 哪一个面叫"上面"取决于
> 分面时定向种子的符号，而那个符号并没有锚定到工位文件上：交换它，两个面的名字会互换，
> 而两面面积、料厚、定向比例**全都一模一样**。报告里因此记录了 `through_axis`（分面认为
> 的"厚度方向"）和一段说明，供人核对。**默认的 `--face auto` 不受影响**，它两面各算一次
> 可达性、取高的那一面，这也是推荐用法。

`plan` 与 `.LS` 导出**刻意分开**：ROBOGUIDE 的坐标系契约（用哪个 `UFRAME`、原点落在
哪里）需要与现场商定，可能只要求重新导出而不必重跑规划。所以 `ls` 只读视点文件，
**不需要数模**。

### 交付物

`plan` 在输出目录写下六个文件：

| 文件 | 内容 |
|---|---|
| `viewpoints.json` | 视点集：位置 + 光轴 + 滚转 + 覆盖点数/面积 + 入射角 + `tracker_ok` + 来源 |
| `viewpoints.csv` | 同一份数据，便于 Excel 目视 |
| `exempt_points.csv` | 被夹持区豁免的点云（供人工核对 CAD 夹持区与实物是否一致） |
| `unreachable_points.csv` | 漏扫点云，**每点带原因**（`blocked_by_part` / `blocked_by_fixture` / `blocked_by_base` / `blocked_by_tracker` / `never_in_view` / `only_poses_that_collide`） |
| `coverage_report.json` | 覆盖报告：覆盖率、视点数、入射角分布、漏扫聚类、占位参数清单、以及**它没有建模什么** |
| `summary.txt` | 上面那些数字的人读版本 |

`ls` 写下 `.LS` + `_points.csv` + `_frame.json`（帧契约）。

### 帧契约（**交付物的语义，不是细节**）

- 视点的 `position` 是扫描头的**测量参考点**（覆盖率计算里那个"距目标点一个工作距离"
  的点），单位 mm，坐标在**数模坐标系**里；
- 局部 **+Z 就是光轴**，从扫描头**指向零件**；
- `.LS` 里的点位是**笛卡尔位姿**，为了对齐这个契约，ROBOGUIDE 侧的 **UTOOL 必须按这个
  参考点教**。教错 → 所有点位的实际测量距离整体偏掉一个常数，仿真里看不出来，实机上
  是系统性误差。

坐标系口径有两条路：把 `UFRAME 1` 教到数模原点（底座固定，只需教一次），或用
`--place "x,y,z,w,p,r"` 把数模摆进 ROBOGUIDE 世界（此时程序用 `UFRAME 0`）。
**无论哪条，都必须先在 ROBOGUIDE 里确认点位落在零件上**，再谈可达性。

### 工位数模

把零件、夹具、底座的 CAD 放进 `input/`，并保证它不进版本控制——那是客户几何。
如果数模是**逐个文件导出**的 IGES，装配位姿会丢失，所以工位建模里包含一个显式、
带自检的对齐步骤，而不是直接信任文件。

## 配置

[`configs/scanner_trackscan49.json`](configs/scanner_trackscan49.json) 存放扫描仪参数。
**其中的值是占位值**：来自公开参数表，以及 "基准距""景深"这两个词的字面几何含义，
**不是**在真机上实测的。其中 `max_incidence_deg`（最大入射角）敏感度远高于其他任何
一个，而它的真值目前未知。

## 数据保密

工位数模、由它派生的一切（网格、点云、视点坐标）以及设计文档**绝不入库**。
`input/`、`output/`、`docs/`、`spike/`、`reference/00_Output Collection/` 全部被
gitignore，并且有自检脚本会在这些东西**一旦被跟踪**时报错：

```bash
uv run python scripts/check_repo_hygiene.py
```

提交前请先跑。被忽略的文件之后仍然可以用 `git add -f` 加进来，但**已经推送出去的
收不回来**。

## 目前的验证情况

在**真实工位数模**上跑过两轮，结论与设计阶段的四轮可行性验证一致：

| 检查项 | 设计阶段（8 mm 网格） | 本次实现复跑（8 mm） |
|---|---|---|
| 上面面积 | 1.0544 m² | **1.0544 m²** |
| 下面面积 | 1.0511 m² | **1.0511 m²** |
| 剪切断面 | 0.0117 m² | **0.0118 m²** |
| 镜像对面命中率 | 99.1% | **99.1%** |
| 定向种子 / 传播 | 88.9% / 99.4%（9 轮） | **88.9% / 99.4%（9 轮）** |
| 料厚（中位） | 0.698 mm | 0.678 mm（光线起点偏置 0.02 mm 所致） |
| 覆盖率 | 99.10% | 99.48%（同一张面、不同抽样，见下） |
| 视点数 | 50 | **50** |

> **覆盖率那一行的 0.38 个百分点不是算法差异，是抽样差异。** 两条依据：
> 一是本实现复刻了第四轮的候选阶梯（同一份配置、逐项相同），两者算出的
> 覆盖率完全一致；二是把**第四轮报告里自己的 154 个漏点**拿来，用本实现的
> 判定规则和一份**逐行照抄的第四轮规则**分别过一遍（同点位、同法线、同求交
> 器）：154 个点的结论**逐点一致，0 处分歧**。差异来自抽样：第四轮抽到的是
> 17033 个点，本次是 16937 个，两套点不是同一批（第四轮的漏点距本次最近的采样
> 点中位 3.32 mm）；而 8 mm 网格下"成型侧壁"那种 1–2 mm 宽的特征上谁被抽中、
> 谁被留下，本身就是抽签。设计 §9.3 记的是同一件事：未播种时同一个输入，覆盖率
> 在 **99.10%–99.48%** 之间跳。本实现三次播种（7/11/13）得 99.48/99.52/99.55%，
> 波动集中在 `never_in_view`（31/17/16），其余成因稳定。
>
> 结论：**把覆盖率当"约 99.5% ±0.1"读，不要追第三位小数**，也没必要为了对上
> 第四轮那个数去改判定规则。

有两条结论影响了设计，也在复跑中重现：

- **固定的单台跟踪器本身不构成瓶颈**，前提是它沿**零件薄轴**方向架设，而不是正对大面
  看过去——机理是零件本体挡住了**扫描头**，不是跟踪器视场角不够；
- 残余漏扫是**二十来处小特征**（窄槽、小凹坑内壁），而不是一整片够不到的区域。

在**交付默认口径**（3 mm 采样网格 + 由粗到细补候选 + `--face auto`）上：

| | 上面（`auto` 选中的） | 下面（对照） |
|---|---|---|
| 贪心集合覆盖后 | 99.50%（103 点） | 91.29%（107 点） |
| 补一轮候选后 | **99.71%（111 点）** | 96.66%（140 点） |
| 补第二轮后 | 99.71%（117 点，只多盖 5 个采样点，第三轮不再获准） | 96.77%（146 点） |

两件事因此有了实测依据：

- **收益在候选密度，不在选择算法**：补一轮把上限抬了 0.21 个百分点（上面），下面抬了
  5.4 个百分点。集合覆盖本身早就把"池子够得着的地方"全盖住了，所以"补齐"那一阶段在
  实测里是空的——**视点数是被候选生成限制的**。
- **"哪一面朝上"的自动判定**用两面各算一次可达性来做：上面 99.71% vs 下面 96.77%，
  差距明显，与设计阶段的结论一致。

一个**取舍**留在这里，因为它是"覆盖率优先"这条排序规则的必然结果：第二轮补候选只多盖了
5 个采样点（119480 中的 0.004%，约 44 mm²），却多要 6 个视点。实现按"先比覆盖率、再比视点
数"取舍，所以留下了 117 点这一版。不想为千分之几个点付 6 个位姿的场合，可以把
`refine_rounds` 设成 1。

这些数字依赖占位的 `max_incidence_deg`，只能当**指示性**参考，因此这里刻意不写出具体数值。
抽样本身还会带来几个千分点的波动（见上一节的说明），所以**报覆盖率请带"约"字**。

### 工位自检在真实数模上报出来的问题

`plan` 每次都先跑一遍工位自检：三套数模是不是真的按工位文件说的那样坐在一起。在真实工位
数模上它报出的是：

> 零件有 **16 个网格点**钻进了夹具内部，最深约 **1.7 mm**（最深点坐标、探针点数与判定依据都写在
> `output/*/coverage_report.json` 的 `alignment_checks` 里，那一层是 gitignore 的）。

这与设计 §4.3 的怀疑一致——**夹具数模是设计版，现场实际夹持区不同**——所以要现场确认夹具
到底压在哪里、是否真的与零件干涉。设计 §4.1.2 当时自检的结论是"无干涉，最小面间距
0.204 mm"，但那个判据是面到面的距离，**看不见几毫米的穿透**；本实现改成有符号判据（零件
表面点落在夹具表面之后，且对附近每一片夹具表面都成立）。

这个判据现在是**确定性的**：它走两套数模自己的几何（零件的顶点与面心，再加按预算铺的面内
格点），一个随机数都不抽，所以换种子答案不变。两处仍然看不见的情况写在
[`scene.py`](src/scanplan/scene.py) 的注释里：整块零件完全埋在夹具体内，以及夹具网格法线
整体反号。

## 报告里必须一起读的三条声明

覆盖面**只是几何可达性**。报告里会显式写明下面三件事，任何引用覆盖率数字的场合都应带上：

1. **不含机器人可达性**：逆解、关节限位、机器人碰撞由现场在 ROBOGUIDE 里判，所以交付的
   `.LS` **可能包含 ROBOGUIDE 判为不可达的点位**——这是预期，不是缺陷。ROBOGUIDE 报
   不可达时**先换 `CONFIG` 构型再试**。
2. **不含机械臂对跟踪器的遮挡**：本阶段没有机器人模型，`tracker_ok` 只对零件/夹具/底座
   判遮挡。现场架设时请同时避开机械臂的常态工作扇区。
3. **哪些参数还是占位值**：报告逐条列出，`max_incidence_deg` 排在最前。

## 原管线与 `.LS` 写入器的关系

[`reference/`](reference) 冻结保留原管线：`PHASE_1`～`PHASE_6`、集合覆盖求解器、以及
IGES→网格转换器。它作为回归基线保留，同时也是新规划器**移植**（而非重写）FANUC `.LS`
写入器的来源——那个写入器已经解决了 FANUC ASCII 格式里一堆繁琐且不容出错的地方
（固定轴 XYZ 欧拉角、万向锁分支、`/ATTR` 自洽、无前导零的数字格式、程序名合法化）。
手册见 [`reference/MANUAL.md`](reference/MANUAL.md)。

**本路线不使用 `PHASE_3` / `PHASE_4` / `PHASE_5`**：它们是 UR5e 逆向运动学与机器人基座
采样、TSP 排序那一层，而本方案整层移除了（见"它明确不做"）。代码没动，只作参考。
